## 1. 项目定位与边界

`rdma_rtl` 是面向 RoCE v2 / InfiniBand RC 风格传输的**发送侧核心逻辑参考实现**，覆盖 QP 状态、BTH/RETH/AETH、PSN 窗口与 Go-Back-N 重传、重传缓存、ACK 超时、错误分类、ICRC-32C 和 DCQCN 简化限速。

当前版本是**可仿真的模块级原型**，不是完整网卡，也不是可上板的完整 RDMA 子系统。

| 能力 | 状态 |
|---|---|
| QP 状态机 | 已实现 |
| BTH/RETH/AETH 封装 | 已实现 |
| PSN 窗口与累计 ACK | 已实现 |
| NAK / 超时 / RNR 重传 | 已实现 |
| 重传缓存 | 已实现，存在【限制】 |
| ACK 超时轮 | 已实现，存在【限制】 |
| 错误分类 | 已实现 |
| ICRC-32C | 已实现 |
| DCQCN 限速 | 原型，存在【限制】 |
| 顶层集成 / RX / DMA / MPT / 队列 | 未实现 |
| 以太网/UDP/IP 封装、综合约束 | 未实现 |

适合用于教学、模块级验证、后续完整发送引擎的基础；不适合直接上板跑真实 RDMA 流量或做协议一致性认证。

## 2. 总体架构

```text
+-------------+          +------+-------+          +------------------+
| dcqcn_rate  |  grant   | psn_manager  |  tx_psn  |    bth_gen       |
| limiter     +--------->| window/ACK   +--------->| BTH/RETH/AETH    |
+-------------+          | NAK/timeout  |          +--------+---------+
                         +------+-------+                   |
                                | rtx_start/rtx_psn          | header
                                v                            v
                         +------+-------+          +------------------+
                         |  rtx_buffer  |          |     icrc32       |
                         | payload store|          | CRC-32C          |
                         +------+-------+          +------------------+
                                ^
                                | ack_en/ack_msn
                         +------+-------+
                         | ack_timer    |
                         | wheel        |
                         +--------------+

qp_fsm: RESET/INIT/RTR/RTS/ERROR -> can_send/can_recv
error_detector: retry/rkey/addr/rnr/link/icrc -> qp_reset_req/rtx_req
```

**预期发送流程**：QP 进入 RTS → DCQCN 授权 → `psn_manager` 给出 `tx_psn` → `bth_gen` 生成头部 → 载荷写入 `rtx_buffer` 并计算 ICRC → 收到累计 ACK 后释放缓存 → NAK/超时从 `base_psn` 重传。

当前仓库**没有** `rdma_tx_engine` 顶层，上述连接是集成约束，不是现成网表。

**时钟/复位**：单时钟域；所有模块 `posedge clk`；低有效异步复位 `negedge rst_n`；建议外部“异步置位、同步释放”；当前无 CDC。

## 3. 公共定义：`rdma_pkg.sv`

|---|---:|---|

**Opcode**：`SEND_FIRST 0x00`、`SEND_LAST 0x02`、`SEND_LAST_IMM 0x03`、`RDMA_WRITE_FIRST 0x04`、`RDMA_WRITE_LAST 0x06`、`RDMA_WRITE_LAST_IMM 0x07`、`RDMA_READ_REQ 0x0A`、`RDMA_READ_RESP_FIRST 0x0B`、`RDMA_READ_RESP_LAST 0x0D`、`ATOMIC_CS 0x11`、`ATOMIC_FA 0x12`、`ACK 0x14`、`RNR_NAK 0x15`、`NAK 0x16`。

**QP 状态**：

| 状态 | 值 | `can_send` | `can_recv` |
|---|---:|---:|---:|
| `QP_RESET` | 0 | 0 | 0 |

## 4. 模块功能

### 4.1 `qp_fsm`

管理 QP 从 RESET 到 INIT、RTR、RTS 的迁移，并在重试超限或访问错误时进入 ERROR。

| 端口 | 方向 | 位宽 | 说明 |
|---|---|---|---|
| `clk` / `rst_n` | in | 1 | 时钟/低有效异步复位 |
| `cmd_i` | in | `qp_cmd_e` | `INIT/RTR/RTS/RESET` |
| `cmd_valid_i` | in | 1 | 命令有效 |
| `retry_exceeded_i` | in | 1 | 重试超限 |
| `access_err_i` | in | 1 | 访问错误 |
| `state_o` | out | `qp_state_e` | 当前状态 |
| `can_send_o` | out | 1 | 仅 `QP_RTS` 为 1 |
| `can_recv_o` | out | 1 | `QP_RTR` 或 `QP_RTS` 为 1 |

行为：必须逐级 `RESET -> INIT -> RTR -> RTS`；`INIT/RTR/RTS` 均可 `CMD_RESET` 回 `RESET`；只有 `RTS` 检测 `retry_exceeded_i/access_err_i` 进入 `QP_ERROR`；`QP_ERROR` 只能通过 `CMD_RESET` 退出。

【限制】`QP_SQE` 未参与迁移；错误检测只在 `RTS` 生效。

### 4.2 `bth_gen`

在 `hdr_en` 有效时锁存并输出 BTH，可选同时输出 RETH/AETH。

| 端口 | 方向 | 位宽 | 说明 |
|---|---|---|---|
| `clk` / `rst_n` | in | 1 | 时钟/复位 |
| `hdr_en` | in | 1 | 头部生成使能 |
| `opcode_i` | in | `opcode_e` | 操作码 |
| `dest_qpn_i` | in | 24 | 目的 QPN |
| `psn_i` | in | 24 | PSN |
| `pkey_i` | in | 16 | Partition Key |
| `ack_req_i` | in | 1 | 请求 ACK |
| `reth_en_i` | in | 1 | 生成 RETH |
| `remote_addr_i` | in | 64 | 远端地址 |
| `remote_rkey_i` | in | 32 | 远端 RKEY |
| `dma_len_i` | in | 32 | DMA 长度 |
| `aeth_en_i` | in | 1 | 生成 AETH |
| `syndrome_i` | in | 8 | AETH syndrome |
| `msn_i` | in | 24 | Message Sequence Number |
| `bth_o` / `reth_o` / `aeth_o` | out | 80/128/32 | 头部 |
| `bth_valid_o` / `reth_valid_o` / `aeth_valid_o` | out | 1 | 单周期有效脉冲 |

行为：输入在 `posedge clk` 采样；输出寄存器化；`hdr_en` 有效后 `bth_valid_o` 拉高一拍；BTH 固定字段 `se/m/pad_cnt/tver/f/b` 当前为 0；`reth_en_i` 与 `aeth_en_i` 可同时有效，但实际协议通常二选一；无 ready 反压，每周期最多一组头部。

【限制】无自动 PAD、无 immediate data、无 IPv6/UDP 封装。

### 4.3 `psn_manager`

维护 `base_psn`、`head_psn`、发送窗口、累计 ACK、NAK/超时/RNR 重传及重试计数。

**参数**：`WIN_SIZE=64`、`MAX_RETRY=7`、`RNR_MAX=7`。

| 端口 | 方向 | 位宽 | 说明 |
|---|---|---|---|
| `clk` / `rst_n` | in | 1 | 时钟/复位 |
| `tx_en_i` | in | 1 | 发送一个 PSN |
| `tx_psn_o` | out | 24 | 当前待发送 PSN |
| `tx_ready_o` | out | 1 | 窗口未满、非重传、非错误 |
| `ack_valid_i` | in | 1 | ACK 有效 |
| `ack_msn_i` | in | 24 | 累计 ACK 的 MSN |
| `nak_psn_err_i` | in | 1 | PSN 错误 NAK |
| `nak_rnr_i` | in | 1 | RNR NAK |
| `timeout_i` | in | 1 | ACK 超时 |
| `rtx_start_o` | out | 1 | 启动重传脉冲 |
| `rtx_psn_o` | out | 24 | 重传起始 PSN |
| `base_psn_o` / `head_psn_o` | out | 24 | 窗口基址/下一个新 PSN |
| `window_full_o` | out | 1 | 窗口满 |
| `retry_cnt_o` / `rnr_retry_o` | out | 3 | 重试计数 |
| `qp_error_o` | out | 1 | QP 进入错误 |

发送规则：`window_used = head_psn - base_psn`（24 位模运算）；`window_full_o = window_used >= WIN_SIZE`；`tx_ready_o = !window_full_o && !rtx_active && !qp_error`；`tx_en_i && tx_ready_o` 时 `head_psn++`，`tx_psn_o` 为加 1 前的值。

ACK 规则：`ack_msn_i` 表示该 PSN 及之前均已收到；仅当 `base_psn < ack_msn_i + 1 <= head_psn` 时 `base_psn = ack_msn_i + 1`；有效 ACK 清零 `retry_cnt/rnr_retry`。

重传规则：NAK PSN 错误时，若 `retry_cnt >= MAX_RETRY` 进入 `qp_error`，否则 `rtx_start` 脉冲、`rtx_psn=base_psn`、`head_psn=base_psn`、`retry_cnt++`；超时仅在 `!rtx_active` 时处理；RNR NAK 在 `rnr_retry >= RNR_MAX` 时进入 `qp_error`，否则从 `base_psn` 重传、`rnr_retry++`；重传期间 `rtx_active=1`，`tx_ready` 被压住，收到 ACK 后清除。

【限制】任意 `ack_valid_i` 即使 ACK 不在窗口内也会清除 `rtx_active`；NAK/超时共用 `retry_cnt`；`MAX_RETRY/RNR_MAX` 被截成 3 位，参数不应大于 7；24 位 PSN 回绕未专门保护。

### 4.4 `rtx_buffer`

按 PSN 保存待确认载荷，支持按 PSN 重传读取和按累计 ACK 释放。

**参数**：`BUF_DEPTH=256`、`DATA_W=64`。

| 端口 | 方向 | 位宽 | 说明 |
|---|---|---|---|
| `clk` / `rst_n` | in | 1 | 时钟/复位 |
| `wr_en` | in | 1 | 写入使能 |
| `wr_psn` | in | 24 | 写入 PSN |
| `wr_data` | in | 64 | 写入数据 |
| `rtx_req` | in | 1 | 重传读取请求 |
| `rtx_psn` | in | 24 | 重传 PSN |
| `rtx_data` | out | 64 | 重传数据 |
| `rtx_valid` | out | 1 | 重传数据有效脉冲 |
| `ack_en` | in | 1 | ACK 释放使能 |
| `ack_msn` | in | 24 | 累计 ACK MSN |
| `usage_cnt` | out | 8 | 当前使用量指示 |

正常行为：写入在 `posedge clk` 生效；`rtx_req` 后一个周期给出 `rtx_data` 和单周期 `rtx_valid`；`ack_en` 清除所有 `psn <= ack_msn` 的有效条目。

【限制 P0】当前实现有两个已确认问题：

1. **写索引不是独立写指针**：`buf_data[(BUF_DEPTH)'((buf_valid))]` 使用 `buf_valid` 位向量的值作为索引，连续写入的索引序列不是 `0,1,2,3...`，而是稀疏跳变，条目可能被覆盖。
2. **`usage_cnt` 不是条目计数**：输出是 `buf_valid` 的低 8 位（位图截断），不是“已用条目数”。测试中的 `rtx_usage=3` 是两次写入后位图 `0b11` 的数值，不是 2 条记录。

此外，ACK 释放使用 `psn <= ack_msn` 的直接比较，不处理 24 位 PSN 回绕。修复前不建议用于完整发送引擎。

### 4.5 `ack_timer_wheel`

为多个 QP 提供基于时间槽的超时提醒。

**参数**：`QP_NUM=1024`、`SLOT_NUM=256`、`TIMER_W=32`。

| 端口 | 方向 | 位宽 | 说明 |
|---|---|---|---|
| `clk` / `rst_n` | in | 1 | 时钟/复位 |
| `start_en` | in | 1 | 启动定时 |
| `start_qpn` | in | `clog2(QP_NUM)` | 启动 QPN |
| `timeout_val` | in | 32 | 时间槽偏移量 |
| `cancel_en` | in | 1 | 取消定时 |
| `cancel_qpn` | in | `clog2(QP_NUM)` | 取消 QPN |
| `timeout_pulse` | out | 1 | 超时脉冲 |
| `timeout_qpn` | out | `clog2(QP_NUM)` | 超时 QPN |

时间模型：内部 4 位预分频，每 **16 个时钟周期**推进一个 slot；`timeout_val` 是 **slot 偏移量**，不是时间单位；实际超时约 `timeout_val * 16` 个时钟周期，另有 slot 对齐误差；最大约 `255 * 16 = 4080` 周期（100MHz 约 40.8us，200MHz 约 20.4us，250MHz 约 16.3us）。

行为：启动时把 QPN 写入 `current_slot + timeout_val` 对应 slot；slot 推进到该位置时 `timeout_pulse` 拉高一拍并给出 `timeout_qpn`；取消会扫描所有 slot，清除匹配 QPN。

【限制】每个 slot 只能保存一个 QPN，后一次启动会覆盖前一次；同一 QP 重启不会自动清除旧 slot，可能重复超时；无冲突链表/溢出队列；`timeout_val` 超出 `SLOT_NUM` 会被截断；同周期 start/cancel 行为依赖 slot 原状态，集成层应避免；测试注释中的“每 32 周期推进”与代码不符，实际是 16 周期。

### 4.6 `error_detector`

把多种错误事件转换为统一错误类型，并给出 QP 复位或重传请求。

| 端口 | 方向 | 位宽 | 说明 |
|---|---|---|---|
| `clk` / `rst_n` | in | 1 | 时钟/复位 |
| `retry_exceeded_i` | in | 1 | 重试超限 |
| `rkey_err_i` | in | 1 | RKEY 错误 |
| `addr_err_i` | in | 1 | 地址错误 |
| `rnr_nak_i` | in | 1 | RNR NAK |
| `link_down_i` | in | 1 | 链路断开 |
| `icrc_err_i` | in | 1 | ICRC 错误 |
| `err_type_o` | out | `err_type_e` | 错误类型 |
| `err_valid_o` | out | 1 | 错误有效脉冲 |
| `qp_reset_req_o` | out | 1 | QP 复位请求 |
| `rtx_req_o` | out | 1 | 重传请求 |

优先级：`retry_exceeded > rkey > addr > rnr > link > icrc`。

动作映射：`ERR_RETRY`/`ERR_LINK` → `qp_reset_req`；`ERR_RKEY`/`ERR_ADDR`/`ERR_RNR`/`ERR_ICRC` → `rtx_req`。`err_type_o` 保持最近一次错误；`err_valid_o`、`qp_reset_req_o`、`rtx_req_o` 都是单周期脉冲，集成层需自行锁存。

### 4.7 `icrc32`

按字节计算 CRC-32C（Castagnoli），用于 RDMA ICRC。

| 项目 | 值 |
|---|---|
| 多项式 | `0x1EDC6F41` |
| 反射形式 | `0x82F63B78` |
| 初值 | `0xFFFFFFFF` |
| 输出 | 按位取反 |
| 测试向量 | `"123456789" -> 0xE3069283` |

| 端口 | 方向 | 位宽 | 说明 |
|---|---|---|---|
| `clk` / `rst_n` | in | 1 | 时钟/复位 |
| `data_valid` | in | 1 | 字节有效 |
| `data_in` | in | 8 | 输入字节 |
| `calc_start` | in | 1 | 重新开始计算 |
| `calc_done` | in | 1 | 结束并输出 |
| `icrc_out` | out | 32 | CRC 结果 |
| `icrc_valid` | out | 1 | 结果有效脉冲 |

使用顺序：`calc_start` 一个周期复位内部 CRC；每周期 `data_valid + data_in`，字节按调用顺序参与计算；最后一个字节的下一周期给 `calc_done`，得到 `icrc_out` 和单周期 `icrc_valid`。`calc_start` 优先级最高，同周期 `data_valid` 被忽略；`data_valid` 优先于 `calc_done`，不要在送最后一个字节的同一周期拉 `calc_done`。无字节计数、无 AXI-Stream，字节顺序和包边界由外部保证。

### 4.8 `dcqcn_rate_limiter`

根据 CNP 和定时器调整发送速率，并用 token 阈值控制发送授权。

| 端口 | 方向 | 位宽 | 说明 |
|---|---|---|---|
| `clk` / `rst_n` | in | 1 | 时钟/复位 |
| `cnp_received_i` | in | 1 | 收到 CNP |
| `tx_request_i` | in | 1 | 发送请求 |
| `tx_grant_o` | out | 1 | 发送授权 |
| `min_rate_i` | in | 32 | 最小速率 |
| `max_rate_i` | in | 32 | 最大速率 |
| `cnp_interval_i` | in | 8 | 增率间隔 |
| `current_rate_o` | out | 32 | 当前速率 |

名义行为：`rate_r` 复位为 `0xFFFFFFFF`；每周期 `token_cnt_r += rate_r`；收到 CNP 时 `alpha` 按 `alpha + alpha/4` 更新，按 `(rate * alpha) >> 8` 降速并夹到 `min_rate_i`；未收到 CNP 时 `cnp_timer` 递增，达到 `cnp_interval_i` 时按 `rate + rate/16` 增率，`alpha` 递减；`tx_grant_o = tx_request_i && token_cnt_r > 1000`。

【限制 P0】当前原型与标准 DCQCN 有明显差距：

1. **CNP 降速实际不生效**：`alpha_r` 复位为 0，更新式 `alpha + (alpha >> 2)` 在 0 时仍为 0，因此 `reduction` 恒为 0。
2. **`max_rate_i` 未使用**：增率没有上限，`0xFFFFFFFF + rate/16` 会溢出到较小值。
3. **token 不消费**：`tx_grant` 只做阈值比较，发送后没有扣减 token，不是真正的 token bucket。
4. **测试存在假通过**：Test 13 的 `dcqcn_rate_decreased` 通过，是因为长时间运行后增率溢出把 `0xFFFFFFFF` 变成较小值，而不是 CNP 降速生效。

该模块应视为算法原型，修复前不要用于真实拥塞控制。

## 5. 参数与配置约束

| 模块 | 参数 | 默认值 | 约束 | 影响 |
|---|---|---:|---|---|
| `psn_manager` | `WIN_SIZE` | 64 | 建议 <= 2^24 | 发送窗口 |
| `psn_manager` | `MAX_RETRY` | 7 | **<= 7** | NAK/超时重试上限 |
| `psn_manager` | `RNR_MAX` | 7 | **<= 7** | RNR 重试上限 |
| `rtx_buffer` | `BUF_DEPTH` | 256 | 建议 2 的幂，<= 256 | 缓存条目数；受 `usage_cnt` 8 位限制 |
| `rtx_buffer` | `DATA_W` | 64 | 与数据路径一致 | 单条载荷位宽 |
| `ack_timer_wheel` | `QP_NUM` | 1024 | 建议 2 的幂 | QPN 位宽 |
| `ack_timer_wheel` | `SLOT_NUM` | 256 | 建议 2 的幂 | 定时精度/范围 |
| `ack_timer_wheel` | `TIMER_W` | 32 | 实际只用 `clog2(SLOT_NUM)` 位 | 超时偏移 |

`MAX_RETRY`、`RNR_MAX` 被代码截为 3 位，超过 7 会静默截断；定时轮实际单位是“16 个时钟周期/slot”，不是时间单位。

## 6. 错误处理与恢复

| 事件 | 检测模块 | 输出动作 | 建议上层行为 |
|---|---|---|---|
| PSN NAK | `psn_manager` | `rtx_start`，从 `base_psn` 重传 | 重发窗口内所有未确认包 |
| ACK 超时 | `ack_timer_wheel` -> `psn_manager.timeout_i` | 同上 | 启动 Go-Back-N |
| RNR NAK | `psn_manager` | 从 `base_psn` 重传，RNR 计数 | 延迟后重试，避免打爆接收端 |
| 重试超限 | `psn_manager` / `error_detector` | `qp_error` / `qp_reset_req` | QP 进入 ERROR，等待复位 |
| RKEY 错误 | `error_detector` | `rtx_req` | 记录错误；通常不应无限重试 |
| 地址错误 | `error_detector` | `rtx_req` | 检查 MR/地址 |
| 链路断开 | `error_detector` | `qp_reset_req` | 复位 QP，重建连接 |
| ICRC 错误 | `error_detector` | `rtx_req` | 丢弃坏包，触发重传 |

当前 `error_detector` 与 `psn_manager` 之间没有自动连线，动作映射需要顶层集成实现。

## 9. 性能与资源说明

- 当前未做综合，以下为结构级判断，不是实测资源数据。
- `bth_gen`、`qp_fsm`、`error_detector`、`icrc32` 为小规模组合/时序逻辑。
- `psn_manager` 为计数器/比较器逻辑，资源很小。
- `rtx_buffer` 使用 `BUF_DEPTH x DATA_W` 数组，通常映射为 BRAM/LUTRAM；当前写索引异常，资源利用不可预测。
- `ack_timer_wheel` 取消操作扫描 256 个 slot，组合逻辑较大；超时扫描为单 slot。
- `icrc32` 每周期 1 字节，若需线速 100G 需并行/流水化。
- 所有模块均为单周期接口，没有流水线反压；高带宽集成时需要重新设计数据通路。

## 10. 已知限制汇总

| 优先级 | 位置 | 问题 | 影响 |
|---|---|---|---|
| P0 | `rtx_buffer` | 写索引用 `buf_valid` 位图值，不是写指针 | 条目稀疏/覆盖，缓存不可靠 |
| P0 | `rtx_buffer` | `usage_cnt` 是位图低 8 位，不是计数 | 上层无法判断真实占用 |
| P0 | `dcqcn_rate_limiter` | `alpha` 初值 0，CNP 降速不生效 | 拥塞控制失效 |
| P0 | `dcqcn_rate_limiter` | `max_rate_i` 未使用、增率溢出 | 速率可能异常跳变 |
| P0 | `dcqcn_rate_limiter` | token 不消费 | 授权模型不真实 |
| P1 | `ack_timer_wheel` | 每 slot 单条目，无冲突处理 | 同槽 QP 互相覆盖/重复超时 |

## 11. 常见问题

**Q1：为什么 54/54 PASS，手册还说有 P0 问题？**
因为 testbench 的预期值有一部分是按现有实现写的，不是按协议语义写的。Test 8 和 Test 13 已明确标注为“编码错误预期/假通过”。修复 P0 后，测试预期也需要同步修正。

**Q2：如何调整发送窗口？**
修改 `psn_manager.WIN_SIZE`，并确认上层能承受相应未确认数据量。`PSN_W=24` 不变时窗口不要接近 `2^24`。

**Q3：如何调整 ACK 超时时间？**
修改 `ack_timer_wheel.SLOT_NUM` 或预分频。当前预分频固定为 16，最大超时约 `(SLOT_NUM-1)*16` 个时钟周期。若需要毫秒级超时，需要增加预分频或改用微秒计时基准。

**Q4：如何增加新的 opcode？**
在 `rdma_pkg.sv` 的 `opcode_e` 末尾追加编码，更新 `bth_gen` 使用方和 testbench。不要修改已有编码。

**Q5：如何验证 ICRC 实现？**
用标准向量 `"123456789"`，期望 `0xE3069283`。当前 Test 12 已覆盖。若要验证字节序，需增加多组不同字节顺序的向量。

**Q6：可以把这个项目直接上板吗？**
不可以。当前没有顶层、RX、DMA、地址翻译、队列管理、以太网封装、时序约束和上板验证。
